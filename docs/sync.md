# Git 同步与人工冲突恢复

`recallcard sync --remote origin` 是用户主动执行的同步入口。Capture、查询、MCP、Native Messaging、Dream 导出及本地状态检查均不会调用此同步入口，也不会自行把资料库上传到远端。

## 初次准备

1. 先用 `recallcard --vault /你的资料库 init` 初始化独立 Vault。Vault 路径必须恰好是 Git 仓库根目录，不能借用项目父目录的仓库。
2. 自行选择可信的私有 Git 远端，检查访问者范围与服务条款，再使用 Git 配置一个明确的远端名称。例如：`git -C /你的资料库 remote add origin 你确认过的远端地址`。命令不会创建远端仓库或选择上传服务。
3. 为该 Vault 配置自己选择的 Git 提交身份：`git -C /你的资料库 config user.name "你选择的署名"`，以及 `git -C /你的资料库 config user.email "你选择的提交邮箱"`。可自行选择 GitHub 提供的 noreply 地址。程序不猜测私人邮箱，不修改身份设置。
4. 确认当前分支与目标远端分支同名。例如本机 `main` 只同步远端 `refs/heads/main`。游离 HEAD 不支持同步。
5. 执行 `recallcard --vault /你的资料库 sync --remote origin`。

远端必须已经配置；`--remote` 接受远端名称，不能直接传 URL、参数或命令。单个远端只能有一个拉取 URL 和一个推送 URL。拉取地址与推送地址可以不同，使用前应自行核对两者。程序不会输出可能含有凭据的完整远端 URL，也不会在交互终端中索取密码；请先用可信的 Git/SSH 凭据管理方式完成认证。

## 一次同步具体做什么

1. 取得与其他写操作相同的本机 writer 锁。未完成的 Dream 事务必须先 `dream recover`；已有 Git 合并、变基、拣选、二分状态、未解决冲突或 `index.lock` 时停止。稀疏工作树的 skip-worktree 标记和 assume-unchanged 标记也会阻断同步，防止正本隐藏于校验之外。
2. 验证 Vault schema、Event 摘要/引用、Memory 结构/证据、抑制记录、Dream 收据和内容寻址对象。检查仓库根目录、已跟踪路径、文件类型与 Git 属性转换规则。
3. 只把白名单内的已完成正本变化暂存并提交。**本地提交发生在任何远端查询/fetch 之前**，所以断网、认证失败或远端拒绝时，已完成的本机事务仍有本地提交。
4. 只查询、拉取明确指定远端的当前同名分支，不拉取 tag 或 submodule，不采用可能扩大的默认 fetch refspec。
5. 检查远端提交树。远端没有同名分支时正常新建；有共同祖先时选择快进或普通双亲 merge。无共同祖先时停止，不使用允许无关历史的合并。
6. 双端同时改动同一个 Memory 或 control 文件时，先停止并报告相关路径和双方提交，**即使 Git 文本合并看起来可行，也不自动裁决**。其他普通文本冲突保留在工作区与 Git 索引中。
7. 合并结果再次校验。分叉合并先以 `--no-commit` 保留待验证状态，通过后才创建 merge commit。快进后的校验失败则保留已整合历史和问题文件，不自动回滚、清理或推送。
8. 执行普通 push，只发送当前分支。禁用 mirror 与自动 follow-tags，不 force push，不 reset/rebase，不删除远端分支，不改写已发布历史。
9. 释放 writer 锁，再调用已有离线重建入口更新 Views 与文本快照。派生重建会自行加锁；若正本推送成功而重建失败，错误会明确区分这两件事，可稍后单独执行 `rebuild`。

同步期间本机其他写操作应重试；不能在另一个 shell 中同时手工修改文件或运行 Git。writer 锁只能约束遵守该锁的 RecallCard 进程，不是跨设备锁，也不能阻止外部编辑器与手动 Git。

返回 JSON 包含本地提交、最终 HEAD、分支、远端名称、整合方式、推送状态及本机重建结果。`recallcard --vault /你的资料库 status` 只读本机 Git 状态，列出变化/暂存/冲突路径和远端名称，不联网。

## 同步白名单

允许的普通、非可执行文件：

- `.gitignore`
- `events/年/月/会话摘要/evt_完整摘要.jsonl`
- `memories/mem_编号.md`
- `control/schema-version.json`
- `control/dream-receipts/dream_完整摘要.json`
- `control/suppressions/evt_完整摘要.json`、`control/suppressions/mem_编号.json`
- `objects/完整 SHA-256 摘要`，文件内容必须匹配名称

不会自动暂存 `.env`、本机凭据、Dream 暂存任务、隐藏旁文件、任意其他笔记、`generated/`、`.index/`、hook、`.gitattributes`、符号链接或 submodule。暂存区/当前提交树如果已经跟踪这些不允许的文件，操作会停止，保留原暂存内容，要求人工整理。正本目录内的非隐藏、不支持文件同样会阻断同步，避免被误认为有效正本。

已跟踪 Event、对象与已完成 Dream 收据只允许追加，不允许借同步修改或删除。新正本若被 `.gitignore` 或本机 Git 忽略规则隐藏，操作会报告错误，不能静默漏传。Memory/抑制记录仍按其显式生命周期变更。

只检查当前待同步树不等于审计整个 Git 历史。过去误提交的秘密即使已删除，仍可能留在历史中；把已有仓库接入同步之前应自行确认完整历史适合发送到该远端。

## 双端重复离线导入同一 Event 的边界

当前单事件段路径由日期、会话摘要与 Event 内容 ID 决定，没有设备名前缀。两台设备离线导入同一来源、同一内容时，可能得到相同 Event ID 与相同路径，但各自的 `captured_at` 不同；两份文件因此不同。

这种情况会留下 Git add/add 冲突，保留两端提交、捕获时间与冲突文件；程序不静默选一边、不改写原始 Event，也不声称 Event 跨设备永远没有冲突。`doctor` 在冲突解决前会明确失败，后续 sync 也会停止。初期建议指定主要采集设备，其他设备先同步再导入同一来源，避免重复离线捕获；需要双端离线采集时，应接受并人工核对这种冲突。独立来源/内容的新增 Event 则可正常普通合并。

## Git 执行与信任边界

程序直接以参数数组执行系统 Git，不拼接 shell 命令或解释远端名称。每次程序调用 Git 都使用独立空 hooks 目录，禁用客户端 hooks、fsmonitor、自动维护与自动签名；拒绝正本上的自定义 clean/smudge filter、工作树编码转换和自定义 merge driver，避免自动转换悄悄改变已验证数据或执行仓库附带程序。`ext::` 外部命令协议被禁用。

这些防护不是不可信 Git 配置的完整沙箱：系统 Git、用户配置的 credential helper、SSH/远端 transport 与登录设置仍必须来自可信来源；远端服务器自己的 hooks 也由服务器管理。程序不会代为安装 helper、执行仓库附带安装程序或修改 Git 安全设置。需要手工签名的策略应在执行前自行确认，不能指望自动同步调用私钥签名工具。

## 出错后怎么处理

### 已有 Dream 事务

先检查并执行 `recallcard --vault /你的资料库 dream recover`。不要删除事务文件来绕过检查；同步不会移动或忽略它。

### 双端修改同一 Memory/control 记录

此时本机变化已提交，远端提交已 fetch，尚未发起自动 merge。记录错误中给出的双方提交，人工比较具体内容、来源、版本与撤回状态。需要合并时可自行用 Git 创建待审合并，逐项保留正确的语义/版本，再通过 `doctor` 检查并自行提交，之后重新执行 sync。不能简单把 “ours/theirs” 当作正确性规则。

结构校验不能判定所有自然语言事实是否相互矛盾；不同 Memory 文件描述同一事实的矛盾仍需要人工审查。本实现不宣称 Git 干净合并就代表事实一致，也不自动调用模型改写冲突。

### Git 文本冲突

用 `git -C /你的资料库 status` 查看冲突文件。程序不会自动删除标记、选边、stash、清理或中止合并。人工处理冲突、检查 `doctor`、完成 Git 提交后再运行 sync；若决定放弃本次整合，应自行确认并使用适当 Git 恢复命令。不要在未理解状态时使用 reset/clean 或强推。

### 查询、拉取或推送失败

本地已完成事务的提交和工作区都会保留。先检查连接、认证与远端配置，再重新执行同一个 sync。若远端在 fetch 后又前进，普通 push 会拒绝；下一次 sync 会重新 fetch/整合，不会覆盖对方提交。程序不会无限网络重试或偷偷改变远端。

### 整合后校验失败

错误会指出校验阶段，且不会 push。分叉 merge 的待审状态或快进历史会保留，不会自动改写回去。先备份当前状态、检查来源/结构/摘要和错误路径，再人工修复或恢复，执行 `doctor`，完成必要的 Git 操作后重试。

### 已推送但派生重建失败

正本已经安全提交并推送，无须删除历史。解决本机权限、占用或损坏的派生目录问题后，运行 `recallcard --vault /你的资料库 rebuild`。向量索引不会自动重新调用模型；没有 embedding 时仍可回退到本地文本检索。

## 撤回与真正删除

同步会传播 suppression 规则与 Memory 状态，但 Git 历史、远端 clone 和已经发给模型的文本不会因此消失。当前实现不会清洗历史，也不承诺“一键彻底遗忘”。需要彻底删除时，必须另行确认每一个副本与历史范围。

## 验证范围

`crates/recallcard/tests/sync.rs` 使用合成 Event/Memory、临时工作区和本机临时 bare 仓库验证同步；不访问真实私人 Vault，不连接 GitHub/互联网，不使用用户凭据。测试覆盖双端新增、非快进普通 merge、快进、语义冲突阻断、未解决文本冲突、未完 Dream、writer 锁、身份缺失、过滤旁文件、克隆重建、hooks/filter 不执行、远端拒推与数据损坏保留等场景。

已实际验证当前 Linux 环境。macOS/Windows 的本机 Git、SSH、路径与文件锁行为仍需各平台验收；不能把可编译或 CI 配置等同于真实平台测试。
