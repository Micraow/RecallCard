# 服务启停代次与停止恢复

本页描述共同 `application::runtime` 入口的生产协议。它不改变来源授权、模型目的地或用户审阅规则；停止请求不能撤回供应商已收到的数据。

## 身份、锁与状态

- 每次首次取得 `service.lock` 独占租约生成随机 UUID 代次，保存为 `ServiceStatus.generation`。进程号、时钟和程序摘要不充当代次。旧状态缺少该字段仍可读取。
- `lifecycle.lock` 只保护代次、租约探测与有界状态文件读写。启动先取得此锁和服务租约，保存新代次，再清理上次已完成的停止记录，最后解锁发布。保存失败保留旧停止记录；崩溃残留的旧 `applied` 记录不匹配新代次。第二实例不能清理现任服务的停止记录。
- 停止调用先绑定持久代次，再等待 `stop-apply.lock`。若等待期间已换代，返回可重试冲突，不执行针对新服务的暂停。原代次正常释放租约不会被误当成换代。
- 在短锁内保存 `recallcard.service-stop/2` 请求，包含请求 UUID、目标代次、时间与 `pending`。随后释放短锁，暂停记忆整理和待处理导入；全部成功后重新取得短锁，仅当完整请求身份仍一致时改成 `applied`。
- `stop-apply.lock` 覆盖整段慢暂停，防止两个停止调用交错，使一个过早宣布完成、另一个稍后暂停新实例。持有短锁时不等待记忆或导入状态锁，避免与检查点反向查询启停状态形成死锁。操作锁的等待上限为 5 秒，超时返回可重试冲突。
- 任何 `pending` 都阻止创建新代次。服务循环与导入调度器只响应本代次的标记；记忆提交检查点和进行中 provider 的取消查询也检查停止标记，不能因慢暂停尚在等待写锁就漏掉停止。

`running` 仍由实际 OS 租约决定。`stop_requested` 说明已持久记录停止意图，不表示所有工作已退出。状态与停止文件只接受有界普通文件（分别 128 KiB / 4 KiB）；符号链接、FIFO、目录、损坏或超限记录按存储错误拒绝，不能在生命周期锁内阻塞等待 FIFO writer。

## 故障与旧记录

暂停中途失败、进程中断或最终确认失败，保留 `pending`，不把未完成状态伪装成成功。用户可明确重试停止：继续同一请求的幂等暂停步骤，成功后才允许下一次启动。不会自动清除记录、自动恢复模型请求或更改预算。

旧版本只有 `requested_at` 的停止记录无法证明慢暂停已结束，按未完成处理；明确重试停止后升级为新版记录。旧的服务状态可以读取，但不承诺新旧可执行文件同时写入不同启停协议的兼容性。应使用同一完整发行物，先停稳旧服务后再启动新版。

## 回归与验证边界

`application::runtime::lifecycle::tests` 使用原创合成资料与显式 channel 屏障：

- 负对照重现旧顺序：服务租约可见后删除停止标记，确定性丢失已成功返回的停止请求。
- 在生产启动 helper 的“已取得租约、尚未发布代次”边界发出停止，校验新代次收到请求。
- 覆盖初始化中的第二实例、慢暂停被真实状态写锁阻挡、并发停止、暂停失败后恢复、旧请求与迟到确认、延迟旧调用、旧格式与非法文件、保存代次失败保留记录。
- 每个合成线程都有显式完成时限，只有确认线程结束后才 `join`；没有用睡眠猜测竞态时序或无限 `join` 等待。

这些测试验证本机协议，不调用真实模型，不代表真实用户验收或跨平台运行验证。普通对话、附件召回与手动复制回归继续由现有工作区测试及原生 CI 执行；准确通过项以对应构建日志为准。
